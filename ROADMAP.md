## v0.5+

- [x] PVC -> FluxVM disk lifecycle (first cut): `spec.volumes[0]` boots from a Bound PVC's `hostPath`/`local` PersistentVolume — see `docs/guides/machine-storage.md`. Still open: multiple volumes per Machine.
- [x] CSI node-plugin integration for network-block volumes (first cut, one backend): `csiNode.enabled` deploys Kairon's own iSCSI-only CSI node plugin (`internal/csinode`). The second deliberate exception to Go-stdlib-only (`google.golang.org/grpc`, `github.com/container-storage-interface/spec`) -- the CSI protocol itself has no stdlib-only wire format. `kairon-node` dials it directly as its own CSI client rather than through kubelet's Pod volume machinery, since a Machine has no backing Pod. No Ceph/EBS/other backends, no CHAP on Kairon's own consumption path (`kairon-node`'s own iSCSI login, distinct from the CSI Controller's own dynamic-provisioning path below). Runs privileged, on a non-distroless base image. See `docs/guides/machine-storage-csi.md`.
- [x] CSI Controller for dynamic iSCSI provisioning, with CHAP and volume expansion (first cut): `csiController.enabled` adds a real `ControllerServer` (`internal/csinode/controller.go`) driving a Linux LIO iSCSI target directly -- `CreateVolume`/`DeleteVolume` provision/tear down a real portal/IQN/LUN per `PersistentVolumeClaim`, indistinguishable from a statically hand-written PV once `NodeServer`'s own `NodeStageVolume` consumes it. A provisioner Secret's username/password (`storageClass.parameters.csi.storage.k8s.io/provisioner-secret-*`) configures real LIO CHAP auth instead of demo mode; `ControllerExpandVolume` grows an existing LUN in place. Real limits: one backing file per volume on whichever single node runs `kairon-csi-controller` (no topology-aware placement across multiple storage nodes); `CreateSnapshot`/`DeleteSnapshot` support is a separate entry below. See `docs/guides/machine-storage-csi.md`.
- [x] CSI `CreateSnapshot`/`DeleteSnapshot` for dynamically-provisioned volumes (first cut): `ControllerServer` now implements both (`internal/csinode/controller.go`), closing what was previously this driver's own explicitly-documented gap. Since a dynamically-provisioned volume is just a flat file under `csiController.volumeDir`, a snapshot is a real file clone (`cp --reflink=auto` -- an instant, metadata-only copy-on-write clone on a filesystem that supports it, e.g. btrfs/XFS-with-reflink, a real byte-for-byte copy otherwise, coreutils' own automatic fallback) into a `.snapshots/` subdirectory, and restoring a new volume from one (`CreateVolume`'s `volume_content_source`) copies it back out before the usual LIO backstore/target/LUN setup runs. Requires the cluster's own `external-snapshotter` stack (the `snapshot.storage.k8s.io` CRDs plus its cluster-wide `snapshot-controller` -- neither installed by this chart, same as every other CSI driver) and the new, separately-gated `csiController.snapshotter.enabled` (off by default, since the sidecar fails to start at all without those CRDs already present). No cross-volume dedup, no incremental/differential snapshots -- each is an independent full clone. See `docs/guides/machine-storage-csi.md`.
- [x] `MachineSnapshotRestore` (first cut): restores one `MachineSnapshot` volume into a new PVC via the standard CSI `dataSource` flow — "restore" and "clone-from-snapshot" are the same operation in Kubernetes' storage model, so this covers both. Deliberately doesn't also create a Machine (point the existing PVC-backed-disk feature at the result instead) — see `docs/guides/machine-snapshot-restore.md`. Needs a real CSI snapshotter behind your StorageClass (confirmed on a real cluster: Rancher's `local-path-provisioner` doesn't have one -- "snapshotting non-CSI volumes is not supported").
- [x] CPU/memory hotplug (first cut): growing `spec.resources` on a Running Machine calls FluxVM's real QMP hotplug (`device_add`/`object-add`, shipped upstream in FluxVM's own `feat/qemu-cpu-memory-hotplug`, PR #62) — see `docs/guides/machine-hotplug.md`. Grow-only (no CPU/DIMM unplug), bounded by headroom reserved automatically at creation (not yet Kairon-configurable), lost across any Machine re-realization (stop/start, cold migration).
- [x] guest-agent (qemu-guest-agent) integration: `spec.guestAgent.enabled` resolves `status.guestIP` via FluxVM's real `guest-network-get-interfaces` (shipped upstream, [zyvorai/fluxvm#63](https://github.com/zyvorai/fluxvm/pull/63)) for network modes with no DHCP lease file (`user`/SLIRP in particular) — see `docs/guides/machine-guest-agent.md`. Graceful-shutdown wiring turned out to be unnecessary: FluxVM's `stop`/`delete` already does ACPI `system_powerdown` with a wait-then-force fallback regardless of guest agent presence. Multi-NIC/IPv6 (`status.guestIPs`) and periodic re-resolution (every 5 minutes once first resolved, instead of once-ever) closed the two gaps this used to list as still open.
- [x] Machine affinity/anti-affinity: `spec.placement.affinity`/`antiAffinity` (required/hard) gate scheduling against other Machines' current placement. Since v0.5, `internal/scheduler` also does real weighted scoring on top of the existing least-loaded/hash-tiebreak baseline: `preferredAffinity`/`preferredAntiAffinity` (soft, weighted), `topologySpreadConstraints` (soft, minimizes matching-Machine count per topology domain; `maxSkew` is also hard-enforced per constraint via `whenUnsatisfiable: DoNotSchedule`, mirroring the Kubernetes field), and a best-effort DRA topology-awareness hint (reads back an already-allocated `ResourceClaim`'s device pool via `ResourceSlice.spec.nodeName`, no role in allocation itself). A Machine using none of the new fields schedules identically to before this scoring pass existed. See `docs/guides/machine-placement.md`.
- [x] `MachineDisruptionBudget`: `evacuate` throttles itself against `minAvailable`/`maxUnavailable` instead of migrating an entire node at once — see `docs/guides/machine-disruption-budgets.md`. Since v0.5, an opt-in validating admission webhook (`webhook.enabled`) also rejects a `MachineMigration` created directly through the API if it would violate a budget — closing the "only gates `kaironctl evacuate`" gap this line used to describe. `kairon-controller` now also reconciles real `status` (`expectedMachines`/`currentHealthy`/`desiredHealthy`/`disruptionsAllowed`) every tick, mirroring a real PodDisruptionBudget's status and closing what used to be documented as "no live status, no controller for this object" — purely observational, `evacuate`/the webhook still each recompute their own allowance fresh rather than trusting it. `evacuate --wait` now keeps retrying (matching `kubectl drain`'s own retry model) until the node is actually empty or `--timeout` elapses, instead of a single pass that left budget-blocked Machines behind for good -- the closest thing to an automatic node-drain Kairon has, deliberately still operator-invoked rather than triggered by `node.spec.unschedulable` on its own.
- [x] `MachineQuota` (namespace-scoped): `maxMachines`/`maxTotalCpu`/`maxTotalMemory`, enforced in `kairon-controller`'s scheduling loop — see `docs/guides/machine-quotas.md`. Since v0.5, the same opt-in webhook above also rejects a `Machine` create that would immediately exceed a quota (matching the reconcile loop's own CREATE-only scope), instead of only leaving it `Pending` — and now also rejects an update that hotplug-resizes an already-scheduled Machine's `spec.resources` past quota, closing what was a real, documented gap (`kairon-node`'s hotplug reconciliation has no cluster-wide quota visibility of its own, so this is the one quota check with no reconcile-loop equivalent to backstop it). `migration.maxConcurrentPerNode`/`maxConcurrentCluster` (a per-node/cluster concurrency cap on in-flight migrations specifically) remains a separate, narrower control this doesn't replace.
- [x] `kairon-ui` in-place password management: self-service change + admin reset (`POST /api/v1/auth/password`, `POST /api/v1/users/{username}/password`), replacing "regenerate a bcrypt hash and redeploy" for named `ui.auth.users` accounts.
- [x] `scripts/deploy-remote.sh --console-tls`: automates (or accepts bring-your-own) TLS material for the kairon-ui↔kairon-node console relay hop, previously a manual step.
- [x] Helm chart hardening: `PodDisruptionBudget` (on by default) and opt-in `NetworkPolicy` for `kairon-controller`/`kairon-ui`.
- [x] Supply chain: Dockerfile base images pinned to a digest, Trivy image scanning in CI, and a tag-triggered `release.yml` that publishes scanned, digest-pinned images to `ghcr.io/zyvorai/kairon-*` — this repo's CI is now the source of those tags.
- [x] SR-IOV/GPU migration capability checks (preflight only, first cut): `internal/controller/preflight.go`'s `deviceClaimsPreflight` refuses live migration of a `spec.deviceClaims` Machine outright -- VFIO passthrough is boot-time-only, and QEMU's live-migration RAM transfer fundamentally cannot carry a passthrough PCI device's in-flight state across hosts without a hot-unplug/hot-plug bracket FluxVM doesn't expose today (it has `HotplugCPU`/`HotplugMemory` but no VFIO equivalent) -- turning a previously silent gap (the device was just left behind) into an explicit, honest rejection instead. Cold migration is allowed when the target node asserts an equivalent device via the new opt-in `kairon.zyvor.dev/vfio-devices` label (the same "operator-asserted, can only confirm a mismatch" honesty `storage-domain`/`network-domain` labels already have) -- cold migration has no state-transfer problem, since the guest is stopped and a fresh runtime created at the target exactly like initial creation. Actually carrying a device through *live* migration remains blocked on FluxVM gaining real VFIO hot-unplug/hot-plug support -- a genuine upstream dependency, not an unpicked Kairon TODO.
- [x] Guest quiesce hooks for snapshots (first cut): a Machine with `spec.guestAgent.enabled` now gets a real `guest-fsfreeze-freeze`/`guest-fsfreeze-thaw` around `MachineSnapshot`'s VolumeSnapshot creation, for an application-consistent snapshot instead of a merely crash-consistent one -- the same mechanism libvirt/virt-manager already use. This needed new support on both sides: FluxVM itself had no `fsfreeze` endpoint at all (its QGA surface was narrow and purpose-built -- network-interfaces, exec, firewall -- though it already had the low-level `qga::raw` plumbing this reuses), so `POST /v1/vms/{id}/qga/fsfreeze`/`fsthaw` were added there first. On Kairon's side, `kairon-controller` (which reconciles `MachineSnapshot`) has no network path to a Machine's FluxVM instance at all -- only `kairon-node` does -- so freeze/thaw is coordinated via a request/response annotation pair on the Machine itself (`kairon.zyvor.dev/quiesce-request`/`quiesce-status`, `internal/controller/snapshot.go` + `internal/agent/quiesce.go`), the same "durable request in the API, not memory" pattern `kairon.zyvor.dev/adopt-only` already established for controller↔node coordination during live migration. A freeze that never confirms within 30s falls back to an unquiesced, crash-consistent snapshot rather than blocking forever; a thaw that fails is retried indefinitely, never silently abandoned, matching `NeedsRecovery`'s own posture. QEMU backend only. See `docs/guides/machine-snapshot-quiesce.md`.
- Cluster API infrastructure provider ("Kubernetes clusters made of Kairon Machines") -- scoped, not built: this is a separate project (its own controller-manager/repository/release, following `cluster-api-provider-<name>` convention), not a Kairon feature PR. Real blocker, not just size: CAPI's whole object graph is built on `metadata.ownerReferences`, confirmed absent everywhere in this codebase (`model.ObjectMeta` has no such field; every parent-child relationship today is a plain name/label reference the reconcile loop resolves itself, e.g. `MachineSet`'s own template-hash label). Two real fits worth keeping if this is ever built: CAPI bootstrap-data Secrets could plausibly be translated into the structured `spec.cloudInit` fields (`hostname`, `user`, `sshAuthorizedKeys`, `packages`, `runCmd`, `writeFiles`; there is no raw cloud-config payload field, so arbitrary bootstrap data needs a translation step or a new field), and `MachineSet`'s own "create/delete to match a template" reconciliation shape is conceptually close to what CAPI expects from an infra provider. See `docs/design-cluster-api-provider.md`.
- [x] TLS certificate hot-reload (`internal/tlsreload`): migration mTLS, the VNC console relay, and the admission webhook all now pick up a renewed leaf certificate/key (e.g. from cert-manager) within 30s, no restart. Only the leaf cert/key -- a CA bundle still loads once at startup. Automated issuance (ACME/cert-manager integration Kairon itself drives) and SPIFFE-style workload identity remain open.
- [x] node fencing (first cut): `kairon-controller` sets a `NodeUnreachable` condition on any Machine whose node stops being `Ready`, every reconcile tick -- detection only, never automatic rescheduling (risks running the same VM twice). `kaironctl fence --reason ...` is the explicit operator-attested action that clears a Machine for rescheduling once a human has confirmed out-of-band the node is truly gone -- see `docs/guides/machine-fencing.md`.
- confidential VM policy (SEV-SNP/TDX) -- verified, still blocked upstream: FluxVM has since (see below) implemented real UEFI Secure Boot/vTPM, but SEV-SNP/TDX are a separate, still entirely-unimplemented gap (confirmed against FluxVM's own source, not assumed -- zero references to SEV/SNP/TDX/confidential-computing anywhere in its crates, a genuine "no firmware/attestation support at all" gap distinct from the OVMF/swtpm work that closed `secureBoot`/`.tpm`). Deliberately not adding a new `spec.security` field for this yet: inventing API surface specifically so it can always be rejected would be speculative, not a real capability with a real caller behind it. Revisit once FluxVM has real SEV-SNP/TDX support to expose.
- [x] OIDC/SSO for `kairon-ui` (first cut): `ui.oidc.enabled`, Authorization Code + PKCE against an external identity provider, alongside `ui.auth.users`. The one deliberate exception to Kairon's Go-stdlib-only design (`golang.org/x/oauth2`, `github.com/coreos/go-oidc/v3`) -- real JWT/JWK verification isn't something to hand-roll. No group-to-admin claim mapping, no SP-initiated single-logout, no refresh-token renewal. See `docs/guides/kairon-ui-oidc.md`.
